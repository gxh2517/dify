# Dify 旧控制台前端的 API 兼容排障

## 旧 Web 构建与新 API 源码不一致时，先以实际请求为准

**问题**：已部署的旧 `.next` 前端请求 `POST /console/api/workspaces/current`，而新版 API 没有对应旧路由，或只提供了 `GET`，导致登录后的控制台显示 `404` 或 `405 method_not_allowed`。

**做法**：按以下顺序定位并修复：

1. 查看 Nginx access log，确认浏览器实际发送的 HTTP 方法和返回状态。
2. 直连本机 API 端口，区分反向代理配置问题和 Flask 路由问题。
3. 使用 `uv run --project /opt/dify/api flask routes` 核对路由是否存在及其允许的方法。
4. 若无法立即重新构建与 API 同版本的 Web，在后端添加最小兼容路由，复用当前的鉴权和工作区响应逻辑，并显式支持旧前端所用的 `POST` 方法。
5. 重启 API 后，以登录态再次请求并确认 access log 中返回 `200`。

**原因**：`405` 说明请求已经到达应用但路由未声明该 HTTP 方法；单纯修改 Nginx 或只增加 `GET` 路由无法满足旧前端。以浏览器真实请求、路由表和直连 API 三项证据交叉验证，能避免把版本兼容问题误判为代理故障。

## 长期修复

将 Web 构建与 API 源码版本对齐后，评估并移除临时兼容路由。

**原因**：兼容路由适合降低恢复时间，但长期保留会扩大 API 的历史行为负担；版本一致才是根因修复。
